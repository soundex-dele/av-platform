# 无人机音视频 SFU 需求符合性与实现可行性评估

评估日期：2026-10-27（北京时间）。需求基线：`D:/workspace/sdk/无人机音视频 SFU 需求说明.md`，V1.11，修订日期 2026-10-27。

本次修订按用户确认：语音为同一无人机与多名用户共同参与的全双工会话，无需私有音频或单人独占；系统没有 TURN，客户端直连 SFU；实时视频使用 UDP、回放视频使用 TCP，均覆盖设备 → SFU 和 SFU → 观看端两段。A-01/A-02 更新含义，新增 V-13/B-07，需求总数由 32 项变为 34 项。

## 结论

**当前项目不能直接满足这份需求，也不能按该文档验收交付；可以保留现有架构，在已有 SFU、WebRTC、SDK 和业务服务基础上补齐。**

已有基础包括多发布者、多轨道、同源多人转发、独立订阅、Opus 双向媒体、VP8 simulcast、NACK/RTX、PLI、上下行拥塞反馈、下行 pacing、整帧准入、JWT 和房间隔离。这使本项目适合作为开发基础，但不等于无人机系统已经完成。

主要阻塞是：

1. SFU 协商、组帧、分包和轨道描述仍限定 Opus/VP8/RTX，未接入 H.264/H.265；没有实时源流自动编码回退闭环。
2. 当前 WebRTC CMake 对 Linux ARM64 明确报错；机载硬编、码率控制及音频设备链路尚需适配。Apple/Android ARM64 构建入口不能替代 Linux ARM64。
3. 多人语音可复用现有房间和多路音频转发；还需无人机业务授权、成员生命周期、端侧多路混音/AEC 及多人实机验证。单人占用和私有音频 ACL 已不属于缺口。
4. 视频 FEC 未接入，重传参数、逐链路质量统计和过载配额不完整。
5. 无人机 Web 多画面、Android/iOS 产品端以及目标设备互通尚未交付；时延、容量和 8 h 稳定性未按该文档验收。
6. 现有媒体链路未按实时／回放强制分配 UDP／TCP，也没有已验证的双段 TCP 直连回放通道。已有 TURN/TCP 和 TCP 文件输入测试均不能满足新增要求；系统方案不采用 TURN。

可以在现有媒体服务架构内实现这些功能，但双段 TCP 回放是新增传输路径，不能只靠打开 TURN 或修改一个 ICE 配置。H.265/FEC、直接 TCP 媒体的三端互通、机载硬件和性能目标必须先做真实媒体验证，不能预先承诺所有端兼容或某个最大路数。

## 关键缺口的实现设计

### 1. H.264/H.265：可实现，但不是打开配置开关

现有底层 WebRTC 已包含 H.264/H.265 RTP 组帧、分包/解包代码，可继续复用，无须从零编写 RTP 协议栈。不过当前 SFU 的 NativeVideoAssembler 固定为 VP8，发送路径直接构造 RtpPacketizerVp8，房间和 SDP 也限定 VP8。

建议按如下顺序改造：

1. 将 codec、fmtp、payload type、RTX apt、关键帧及参数集信息贯穿 Source、Output 和原生收发适配器；按 codec 使用相应原生组帧/分包器。
2. 实现 H.264/H.265 的协商能力注册、参数匹配及重新协商，补 SPS/PPS、VPS、分片、关键帧和 SSRC/时间戳重建测试；SFU 继续保持不解码、不转码。
3. 机载 SDK 接入目标 SoC 硬件编码器，贯通码率控制、请求关键帧、动态分辨率和错误状态。默认 builtin codec factory 没有提供 H.265 编解码器，不能把 `RTC_ENABLE_H265` 当成可用硬编实现。
4. 针对目标 Web/Android/iOS 做实际接收解码验证，再发布兼容矩阵。H.265 在某设备可播文件，不代表同一设备 WebRTC 可协商播放。

实时源流编码状态机建议使用：`H265_ACTIVE → SWITCHING_TO_H264 → H264_ACTIVE`，所有事件附带 streamId 和 codecEpoch。首位观看者不支持 H.265 时直接要求 H.264；任一有效、已授权且支持 H.264 的 H.265 不兼容观看者加入，触发该实时源流切换；只要仍有此类观看者，禁止切回 H.265。

切换操作要串行化：确认权限和能力 → 通知源端 → 建立 H.264 发布与接收协商 → 确认关键帧/参数集及媒体就绪 → 切换所有订阅映射 → 撤销旧轨道。可用短时双轨准备或停旧重建，取决于机载编码通道和可接受中断；需求并未要求零中断。不能只给新加入者发 H.264、让原观看者继续 H.265，也不能无限期双发。

若失败或超时，应显示明确状态、清理半完成轨道并保留一致的代次。无不兼容观看者后，可以继续 H.264；原需求没有要求立即自动升回 H.265。若实现升回，需要额外防抖和资源验证。

**回退只作用于实时流。** H.265 回放遇到不兼容端，必须由外部发布模块提供兼容回放源，或者调整明确的兼容范围；不自动把实时回退规则扩展成 SFU 回放转码。若要求任意不支持 H.265 的终端播放任意 H.265 回放，同时拒绝所有兼容源/解码适配，则纯转发 SFU 无法做到，应在验收前确认此边界。

### 2. 多人语音：复用房间转发，补端侧混音与成员管理

需求已取消每机唯一发言者和私有音频，因此不再需要为此新增独占锁、busy 仲裁、每次一对一私有音频房间或音频发布者级 ACL。现有房间内多发布者、独立轨道转发更接近新需求；Rooms::subscribe 遍历其他参与者轨道，默认不回送自己的音频。

建议每架无人机一个逻辑媒体房间，实时 WebRTC 视频与多人音频可共享相容的媒体连接；回放使用独立 TCP 通道，按相同设备/会话身份授权。所有获授权语音参与者可接收同会话其他人的音频。业务服务仍负责谁能加入/发布/订阅、授权有效期及撤权，不需要私有音频不等于匿名访问。跨设备观看不能隐式将不同设备的语音合并。

SFU 独立转发各路 Opus，端侧解码并混音播放，无需先建服务端混音。AEC 必须使用最终混合播放信号作为参考，验证无人机扬声器与多用户同时发言，避免把某一路播放参考误当完整参考。当前多人音轨支持基础不能替代至少“无人机+两用户”的同时说话、用户互听与实际听感验收。

成员管理最少包含 deviceId、sessionId、memberId、幂等 requestId、connectionEpoch、到期/心跳和条件清理。单成员退出不关闭整个会话，旧连接事件不能撤掉新连接；语音退出需仅清理语音资源，不能无条件踢出仍有视频观看权限的用户。现有远控服务可参考授权/代次/撤销模式，但不复用其独占业务语义。容量不足返回容量原因，不伪装成单人对讲占用。

### 3. Linux ARM64 与故障隔离：先补可运行的机载基础

`webrtc/cmake/platform.cmake` 仅在 `(APPLE OR ANDROID)` 时接受 arm64/aarch64，因此 Linux ARM64 当前不是“尚未测试”而是现有配置明确不支持。

需要补工具链/sysroot、依赖架构、NEON 与平台源文件选择、Linux 音频/视频采集后端，再接目标 SoC 硬件编码。摄像头稳定身份应来自平台持久设备路径/硬件标识及业务映射，不能长期依赖枚举序号。

当前媒体 pump 的错误可能传播到整个 Room，必须改为单轨错误隔离：摄像头不可用 → 报告状态 → 仅停该源 → 保持其他视频与语音 → 重试/重新发布且增代次。补“设备未返回错误但一直不出帧”的超时检测。独立 TCP 回放连接也必须有自己的失败与清理边界，不能因一路回放故障停止整机媒体。

### 4. 视频 FEC：按两段链路接入，不能直接透传所有冗余包

可复用 WebRTC 的 ULPFEC/RED 或 FlexFEC 原生实现，但具体方案取决于目标端对相应编码和 FEC 的协商支持。实时 UDP 链路需要分别验证无人机→SFU 和 SFU→观看者。若回放采用非 RTP 的 TCP 协议，按 V1.11 的 QoS 适用性单独记录可靠传输和恢复机制，不把 TCP 重传记为 RTP FEC 已通过。

当前 SFU 会重写序号、SSRC 并重新分包，因此上行产生的 FEC 校验关系不能不加处理地用于下行。通常需要上行恢复后再转发媒体，并按下行新包序列生成对应 FEC，或者使用经验证保持保护关系的专门路径。这属于媒体传输适配，不需要视频转码。

Opus 带内 FEC 由编码端产生、接收端恢复，SFU 不解码音频即可转发；需要确认实际协商、启用条件、码率和丢包下恢复统计。所有冗余/RTX/padding 都计入预算，不用增加冗余掩盖链路容量不足。

### 5. QoS、统计与容量：保留现有机制，补配置和可验证闭环

既有 GoogCC、NACK/RTX、PLI、pacing 和独立订阅值得保留。需要补齐硬件编码器响应反馈、单层源暂停策略、音频不可用提示、重传缓存/次数/窗口配置、逐链路日志和 1 s 采样。

SDK 视频实际解码已进入媒体图，不能直接把 WebRTC `framesDecoded` 当作最终播放帧数。应在图内记录解码/呈现帧、冻结和队列，在音频输出记录中断；所有指标关联 streamId、sessionId、viewerId、方向和连接代次。累计计数器取增量、重连重置基线，并注明码率及丢包率统计口径。

容量测试严格按原文单层 H.265 720p30、2 Mbps/路、Opus 32 kbps/发布源及安全/QoS配置；H.264 单列，切换峰值另计。实时 UDP、回放 TCP 和多人语音的混合负载分别记录，TCP 回放须计入连接、缓冲、重传及 TLS 成本。包含无人机在内的 N 个全互听发言端对应 N 路音频源、N×(N−1) 份转发，每份订阅计入出口带宽；实际 DTX/同时发言情况另记。不能拼接独立最大值。补总源流、订阅、连接、带宽和缓存配额后，在候选最高通过负载完成 8 h。

### 6. 实时 UDP 与回放 TCP：直连 SFU 的两条媒体路径

用户已明确系统没有 TURN。设备和观看端均直接访问 SFU 可达媒体端点，部署必须保证相应 UDP/TCP 端口和地址可用。不能把 TURN/TCP、TCP 信令或设备从 TCP 输入读取文件当作 TCP 回放实现。本仓库历史 TURN 测试仅是已有模块记录，不属于本系统部署或验收方案。

**实时 UDP：** 保留 WebRTC 的 DTLS-SRTP 媒体路径，约束发布与订阅两侧实际选中的媒体传输为 UDP，不配置 TURN，不静默回退 ICE-TCP。候选配置、服务端端口和连接状态检查要形成闭环；用实际 selected candidate pair 和抓包记录分别验收，两端重连或编码回退后重新检查。现有 SDK `relay_only` 表示只选中继，并不是 TCP 开关；无 TURN 方案不能启用它。

**回放 TCP：优先评估 SFU 内独立的 TLS/TCP 媒体接入与分发模块。** 设备读取录像并形成带 codec/参数集、时间戳、关键帧标记、streamId/playbackSessionId/publishEpoch 的编码帧或媒体片段，通过直接 TCP/TLS 连接发布给 SFU。SFU 以一份源流服务多份独立 TCP 订阅，保持内容不转码、进度不误合并，不接收文件路径、不提供录像目录或文件点播。

Web 端不能任意打开原始 TCP socket，可评估直接连接 SFU 的 WSS 媒体端点，再由 MSE（适合的 fMP4 等封装）或 WebCodecs 播放；Android/iOS 使用匹配的 TCP/TLS 接收和解码路径。WSS 此处必须真正携带回放视频，不只是信令；基于 HTTP 的替代实现也须排除 HTTP/3/QUIC 这类 UDP 路径。MSE/WebCodecs、H.265、TLS 和时间戳兼容性都需按目标端验证，不能先声明三端可用。传输封装转换可以需要，但不等于视频解码转码。

若希望所有媒体继续沿用 WebRTC，可先做“设备直连 SFU ICE-TCP + 各观看端直连 SFU ICE-TCP”可行性验证；只有两段真实媒体协商、传输和播放通过才可采用。当前代码/测试没有证明该能力，不承诺仅设一个 transport 参数即可实现，也不使用 TURN 代替直连。实时 UDP 与回放 TCP 必须使用独立传输，不能把二者放进同一个 BUNDLE 连接后按轨道名称声称协议不同。

TCP 回放新增工作包括：应用帧/片段边界、参数集和关键帧缓存、身份与订阅权限、每订阅有界队列、异步发送/背压、写入超时、停流/EOS/重连代次、客户端解码呈现及监测。慢观看者仅暂停/断开自己的回放订阅，不能阻塞共享源和其他观看者；需从可解码边界恢复。TCP 可靠性不保证低时延，正常网络回放 P95 ≤500 ms 仍须遵守；若所选封装需长缓冲而达不到，应调整实现，不擅自放宽指标。

建议先完成一条真实录像“设备 TCP → SFU → 浏览器 TCP”的最小通路，并在同时运行实时 UDP 和多人语音时分别限制/阻断 UDP 或 TCP，验证协议不切换、故障互不传播。再扩展到移动端、多人分发和容量测试。该新增模块可以复用鉴权、源流标识、订阅路由和配额模型，但不能直接复用所有 WebRTC 传输与播放代码。
