# AV Platform 代码规范（第一版）

本规范用于新增代码和后续修改，重点覆盖原生 C/C++ 与 Objective-C/Objective-C++。本次引入只添加配置和文档，不格式化存量源码，不改变构建、子模块指针或公共 API。历史代码不要求一次性达标；格式调整应控制在本次改动范围内，大规模整理另行提交。

## 1. 适用范围与优先级

- 统一格式适用于 `livekit-sdk-cpp`、`livekit-app`、`livekit-cpp` 中本项目维护的原生代码。整个 `graphflow-cpp`（含 `utoolkit`）遵循其模块惯例，已从统一格式化范围中排除。
- WebRTC、第三方依赖和上游协议快照遵循各自规范，不批量套用平台格式。生成代码应修改生成器或源定义，不手工排版。
- 根目录 `.clang-format` 是统一排版基线；路径下已有更近的 `.clang-format` 时，`--style=file` 优先使用该配置。根目录配置不会覆盖 WebRTC 自带配置。
- 子模块放在本聚合仓库下时可以向上找到根配置；单独克隆子模块时不会带上它。适用统一格式的子模块独立开发时应使用相同版本的工具，并显式引用聚合仓库配置，或经模块维护者约定将配置同步到子模块。
- Go 使用 `gofmt`，Web、Python、CMake 等遵循各模块已有工具与约定，不交给 clang-format。C++ 语言标准以目标的 CMake 设置为准：当前 SDK、客户端和媒体服务主要使用 C++20，GraphFlow 使用 C++17；不得为了排版升级语言标准。

## 2. clang-format 安装与使用

统一使用 **clang-format 20.1.8**，避免版本差异导致重复改动。忽略文件使用 `**` 递归匹配，依赖 clang-format 20 起提供的支持，不应使用旧版本替代。格式工具版本与编译器版本独立。可安装对应 LLVM 发行版，或在 Python 虚拟环境中安装固定版本：

```sh
python -m pip install clang-format==20.1.8
clang-format --version
```

以下命令从聚合仓库根目录执行。检查命令不写回源文件；有排版差异时返回非零退出码：

```sh
# 只读检查一个明确指定的文件。
clang-format --style=file --fallback-style=none --dry-run --Werror livekit-sdk-cpp/include/livekit/rtc/engine.hpp

# 输出格式化预览到终端，不修改文件。
clang-format --style=file --fallback-style=none livekit-sdk-cpp/include/livekit/rtc/engine.hpp

# 后续确需排版时，仅对选定文件显式使用 -i。
clang-format --style=file --fallback-style=none -i path/to/changed_file.cpp
```

存量文件可能检查失败，这不代表配置无效，也不要求顺带整理整份文件。修改历史文件时可通过编辑器“格式化选区”或 `--lines=起始行:结束行` 限制范围；clang-format 可能扩展到所在语法单元，提交前仍需审阅 diff。新文件应完整满足格式检查。

`.clang-format-ignore` 排除 GraphFlow、上游、第三方、构建目录和常见生成文件。它在支持该机制的命令行工具直接接收文件路径时生效；通过标准输入工作的编辑器或封装工具可能绕过忽略规则，嵌套的忽略文件也可能替换父级规则。不要依赖它执行全仓库扫描或批量写回，始终只向工具传入适用统一格式的原生文件；编辑器中也应为 GraphFlow 保留模块自身设置。

当前 Windows 环境的 clang-format 20.1.8 会将 `playout/` 误匹配到 `**/out/**`，并可能在成功退出时返回空输出；`src/media_nodes/playout/.clang-format-ignore` 已通过目录级规则覆盖避免误排除。封装脚本必须先完整读取输入、检查进程退出状态，并拒绝将非空源码替换为空输出；不要将格式化输出直接重定向回输入文件。格式检查成功也可能表示文件被忽略，应确认预期文件实际参与了处理。

编辑器选择 clang-format 20.1.8，样式设为 `file`。第一阶段建议手动格式化选区，避免保存历史文件时自动改写全文。本次不启用保存时格式化、Git hook 或全量 CI 格式门禁。后续接入 CI 时先检查新增文件和变更范围，历史格式债务单独治理。

## 3. 排版规则

| 项目 | 约定 |
| --- | --- |
| 基础风格 | Google，以下列显式配置为准 |
| 缩进 | 2 个空格，不使用 Tab；续行缩进 4 个空格 |
| 行宽 | 100 列；不可拆分的标识符、URL 等允许超过 |
| 花括号 | 左花括号与声明或控制语句同一行 |
| 控制流 | `if`、`else`、循环始终使用花括号，避免一行多条语句 |
| 短函数 | 仅空函数允许单行；非空函数展开 |
| 指针与引用 | `Type* value`、`const Type& value` |
| 类访问标记 | `public:`、`protected:`、`private:` 比成员少缩进 1 个空格 |
| 命名空间 | 内容不额外缩进，结束处保留命名空间注释 |
| include | 保留原有顺序和分组，不自动重排平台相关头文件 |
| 注释 | 不自动重排注释文字；人工保证可读性 |
| 文件编码 | 新文件使用 UTF-8；新建原生文件优先 LF，现有文件避免无关换行符变更 |

clang-format 负责空白、换行和排版，不负责命名、添加控制流花括号、检查所有权或保证语义正确。上述人工规则仍需代码审查。

```cpp
namespace av {

class FrameQueue {
 public:
  bool push(const Frame& frame) {
    if (closed_) {
      return false;
    }
    return enqueue(frame);
  }

 private:
  bool enqueue(const Frame& frame);
  bool closed_ = false;
};

}  // namespace av
```

## 4. 命名与接口

- 适用统一规范的新建独立 C++ 模块默认：类型使用 `PascalCase`，函数、局部变量、参数使用 `snake_case`，私有数据成员使用 `snake_case_`，常量使用 `kPascalCase`，宏使用带模块前缀的 `UPPER_SNAKE_CASE`。
- 扩展既有类或 API 时优先保持周边命名。GraphFlow 整体沿用其模块惯例，例如 `loadFromNodes` 与 `m_paths`。不为统一命名改动公共接口、序列化字段、协议字段或跨语言绑定。
- 文件使用有业务含义的 `snake_case`，头文件沿用所在模块的 `.h` 或 `.hpp`，实现文件沿用 `.cc` 或 `.cpp`，不批量改扩展名。
- 名称表达单位和语义，例如 `timeout_ms`、`sample_rate_hz`、`frame_count`；优先用 `std::chrono` 表达时长，避免混用时间戳、时长和不同时间基。
- 公共接口说明所有权、可空性、线程约束、回调执行线程、失败方式和有效期。新增参数优先提供清晰的类型，避免难以理解的多个布尔参数。

## 5. 头文件与依赖

- 头文件应可独立编译，直接包含其使用类型的必要声明，不依赖其他文件偶然引入的头文件。沿用模块的 `#pragma once` 或 include guard。
- 实现文件优先包含对应头文件，其余按标准库、第三方、项目内头文件分组；有顺序要求的平台头文件保留必要顺序并注明原因。工具不会自动调整这一顺序。
- 不在头文件中使用 `using namespace`。内部实现放入匿名命名空间或 `detail`，避免泄漏到公共 API。
- SDK 公共头文件尽量不暴露 WebRTC、FFmpeg、Qt、ImGui 等后端细节。平台差异集中在适配层，减少散落的条件编译。

## 6. 生命周期、所有权与错误处理

- 使用 RAII 管理内存、线程、文件、设备、锁和系统句柄。默认采用值语义或 `std::unique_ptr`，确有共享生命周期才使用 `std::shared_ptr`，避免引用环。
- 裸指针和引用默认表示借用；跨线程、异步任务和回调中的借用必须有明确的存活保证。不要在可能晚于对象销毁执行的任务中无保护地捕获 `this`。
- 用 `const` 表达只读，单参数构造函数按需声明 `explicit`，覆盖虚函数使用 `override`。不确定不会抛异常时不要添加 `noexcept`。
- 沿用所在模块的错误模型，不混用模糊的返回值和异常语义。错误应携带可定位的上下文，不吞掉失败；析构和跨 C ABI、系统回调边界不能让异常逃逸。
- 日志包含必要的会话、轨道或操作标识，不记录令牌、密钥和完整敏感媒体数据；高频路径避免逐帧同步日志。

## 7. 音视频流水线与并发

- 新增或改造音视频流水线时尽量优先使用 `GraphEngine`。业务层负责场景编排，节点负责明确的媒体职责，后端适配层负责设备与协议实现。
- 明确控制线程、采集线程、编解码线程和回调线程的职责。生命周期操作遵循所在引擎约定，不在同步媒体回调内重入启停、销毁或重建图。
- 关闭时先停止接收新工作并让生产者静止，再按依赖顺序取消任务、解除回调、等待线程退出并释放资源。清楚定义重复关闭和部分启动失败的行为。
- 队列必须有容量或资源上限，定义背压、丢帧、超时和取消策略。不要把缓冲区持续增长当作处理速度不足的解决方式。
- 锁保护范围应小且明确；避免持锁执行外部回调、阻塞 I/O、等待任务完成或销毁可能等待其他线程的对象。共享状态注明锁或线程归属，不能用 `volatile` 替代同步。
- 实时音频回调和关键媒体路径避免阻塞、不可控分配及重型日志。帧结构明确格式、尺寸、stride、时间基和缓冲区所有权；零拷贝前先保证生命周期正确。

## 8. 验证与提交

- 功能改动执行受影响目标的编译、相关单元/集成测试；平台专属代码在对应平台验证，未验证项如实列明。
- 按仓库协作约定，使用无窗口测试与程序内渲染截图验证；不使用 computer-use 或桌面自动化操作用户应用。
- 自动化检查与实际设备人工验收分开记录。无窗口测试通过不代表真实摄像头、麦克风、扬声器或显示设备已经人工验收。
- 提交前检查 diff，只保留与任务相关的变更；不要把批量排版、公共接口改名与功能修复混在一起。
- 聚合仓库与子模块分别检查状态。先在子模块中完成本地提交，再更新并提交主仓库的子模块指针；不要求先上传子模块提交。
- 提交与推送分别处理。用户要求“提交代码”时默认只完成本地提交；仅在用户明确要求推送或上传时执行远程推送。
